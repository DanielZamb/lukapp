# C02 contract sketch

Public calls retain the existing Owner/device proof wrappers and server-derived Actor.

- `createUserCategory({name, selection, idempotencyKey})` accepts a concept preset or an explicit four-answer nature selection. Expense/Income create a stable Workspace category. Still-mine/debt returns a profile route without inserting a category.
- `suggestCategoryNature({name})` returns a versioned suggestion requiring confirmation. Matching ignores case/accents, accepts edit distance one only for names of at least four letters, and returns all tied concepts in sorted order. Account resolution searches only the confirmed nature; ties and unknown names use the template's Otros account.
- `listUserCategories` and `categoryTotals` read Workspace records and actual immutable signed Journal Lines.
- `changeUserCategory({categoryId, revision, change, confirmed:true, idempotencyKey})` renames, archives, merges, or changes the future default account. Merge archives the source and links its stable identity to the target; historical totals remain on their original IDs. No Posted line changes.
- Cash commands accept `userCategoryId` and optional `categoryRevision`; an advanced account override retains the template use guard. The counterpart line stores an immutable category snapshot and actual account provenance.
- `previewCategoryReclassification({categoryId,target,currentDate})` derives signed outstanding amounts by period/account from all annotated history, including reversals and earlier corrections. It returns source references, counts, money, locked impact, planned dates and a full revision token.
- `confirmCategoryReclassification({...preview request, revisionToken, confirmed:true,idempotencyKey})` rechecks authority and token, posts one correction per open period and one labelled locked-period catch-up through shared Posting, then advances the category revision. One Convex transaction owns corrections, category state and receipt. Retry returns the same receipt; changed facts conflict.

Ownership: category policy owns normalization/presets/resolution; category commands own lifecycle; reclassification owns preview/correction intent; Posting owns ledger writes and accounting invariants; Convex store owns persistence only. No second ledger or projection. Corrections keep the category on reversing lines; replacement P&L lines carry the new snapshot. Balance-sheet conversion creates a profile through canonical setup, retires the category, and leaves replacement lines associated with that profile through their account. Recovery receives no mutation hook.

New profile kinds use required classification facts: receivable security plus an external counterparty name, investment form (term deposit/fund), and personal-debt external counterparty name. These facts are descriptions of external persons, not a new settlement subledger. Existing kinds retain their contract. Parent mappings come from the actual two templates; canonical setup asks for money held/receivable or debt still owed and posts its normal-side opening.

The current-date period must already be open for locked catch-up. Never open or reopen it as a workaround. The catch-up date cannot precede any locked source date. Open historical corrections use the latest affected source date in their month. Profile conversion opening must precede all correction dates. A real changed circumstance creates a new category. Future template account replacement uses the same preview/confirm target-account mechanism.

## Reviewable behavior and native handoff

The four answers are `Expense`, `Income`, `stillMine`, and `payingDebt`; custom creation must carry `confirmation: answered | lexiconConfirmed`. The latter must match a current backend suggestion. Preset selection uses its fixed nature. A name can receive multiple suggestions (`arriendo` and `interest`); no suggestion grants authority. Generic `seguro` is deliberately ambiguous between life and vehicle insurance within Expense and uses Otros until an advanced review. Unknown Income names use the Income Otros account. Short words accept exact spelling only; names of at least four letters accept one insertion/deletion/substitution. Prefixes `préstamo a`/`loan to` and `deuda con`/`debt to` suggest the profile answers. Version `category-es-en@1` fixes these decisions.

Required profile answers are `classificationAnswers`:

- Receivable: `kind: receivable`, `security: secured | unsecured`, nonblank `counterpartyName`. Ask whether backed by real collateral and who owes the money. The name is preserved product evidence; it creates no Open Item or settlement Counterparty entity.
- Investment: `kind: investment`, `form: termDeposit | fund`, optional operator `counterpartyName`. Ask term deposit versus fund; position/tax-lot valuation is deferred.
- Personal debt: `kind: personalDebt`, nonblank `counterpartyName`. Ask who is owed and how much remains owed at the Start Tracking date. Colombian parent is `219505`, US parent `2120`.

Use `setupFinancialAccount` for atomic product/opening setup, or the existing create and opening calls. The profile's opening amount means its balance at the supplied opening date, including debt still owed then. Retroactive conversion requires that opening date on or before every correction date and an unlocked opening period. Record a genuine changed circumstance using a new category/profile rather than this retroactive command.

Cash entry callers can bind `categoryRevision` to the category they reviewed. A mismatched current revision fails. A successful cash retry uses the immutable original snapshot even after rename/archive/default changes; a changed category, override or other submitted fact conflicts. `listUserCategories` includes archived and converted records for stable history; posting accepts only active resolved records. Rename keeps classification fixed. Merge retires the source with `mergedIntoCategoryId`; callers select the target for future input. `categoryTotals` retains historical identities and separately sums signed Expense and Income annotations by actual accounting month, including catch-up effects. No silent historical rollup occurs.

Reclassification transfers the signed counterpart amount without changing cash. An Expense debit reclassified to Income becomes a Revenue debit (negative Income), not an invented cash receipt. Preview `amount` is gross absolute root-attributed exposure still needing correction, including opposite signs that cancel at the account level, with `lockedAmount` the locked portion; `entryCount`/`lineCount` count source history used by the selected correction buckets, including prior corrective entries. Accounts already aligned with the requested nature/account are excluded from amounts, dates, counts and locked-period requirements. Empty root buckets require no correction. The revision token still binds all annotated category history. Confirmation consumes exactly this selected preview plan. The buckets expose exact signed amounts, source lines and root attribution. Confirmation uses the entire `revisionToken`, `confirmed:true`, and one fresh idempotency key. Category change requests also require the exact revision and confirmation. A failed transaction leaves no correction, materialized target account, category revision, receipt or effect fact.

## Accounting to Recovery seam agreed with C04

`journalSourceEffects` rows are immutable `{workspaceId: Id<workspaces>, sourceEntryId: Id<journalEntries>, journalEntryId: Id<journalEntries>, expenseDeltaMinorUnits: number, sourceSequence: number}`. `sourceEntryId` always identifies the ORIGINAL cash source; `journalEntryId` identifies the producing correction or correction reversal. Index `by_workspace_source` is `[workspaceId,sourceEntryId]`. `sourceSequence` starts at one and increases per Workspace/original source; the same Posting mutation reads the indexed source range and assigns max+1. It provides a causal ordering when producing timestamps tie. Replays allocate no sequence. C04 must freeze the activation sequence and evaluate later causal prefixes; timestamps serve display/as-known-at evidence and cannot order ties. Posting writes these facts in the same transaction as the entry and category receipt. Deltas are safe signed minor units: Expense to Expense zero/no row; Expense to Income/Profile negative; restoration positive. A correction reversal writes the mirror exactly once. Reader sums all rows, including both the correction and its reversal; filtering reversed corrections would double restore eligibility. Original cash reversal remains a separate `by_reverses` exclusion.

C04 owns the indexed reader and Recovery authority. It preserves original amount/date, derives current eligibility from original principal plus all linked deltas, and applies ADR-0075 suspension from source reductions. Corrections never become new Recovery candidates. C02 never writes Recovery state. The coordinator must prove the actual C02 writer with the reviewed C04 reader at integration; C02 standalone tests prove actual public correction/reversal writer facts but do not prove that combined reader.

Write trace: public `confirmCategoryReclassification` -> unchanged Owner/device wrapper -> AccountingCore -> reclassification command -> shared `postJournalEntry` -> Convex store atomically inserts immutable entries/lines/source facts and receipt. Read trace: public `categoryTotals` -> Owner/device wrapper -> core category query -> actual Stored Journal Entries/Lines -> signed monthly totals. One General Ledger owns money throughout.
