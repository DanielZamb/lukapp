# Savings Recovery backend contract

Recovery owns backend Draft plans, frozen activated commitments, immutable planning events, and retry receipts. Its `RecoveryLedger` type exposes only accounting reads. The adapter constructs that port explicitly. Accounting commands do not call Recovery.

Every public `savingsRecovery` export uses A02's `ownerMutation` or `ownerQuery` and the shared operation registry. Arguments contain Workspace ID and device proof, never an actor. Current membership is read on every request. `workspace-roles@3` grants `manageRecoveryPlans` only to Owner; View grants reads. Posting Authority does not grant Recovery Plan Authority. Business and multiuser grants remain deferred.

Commands return stable record IDs. All writes take a Workspace-scoped idempotency key. A retry with the original request returns its stored result before checking changed ledger facts, but still checks current membership and authority. Changing facts under that key conflicts. Draft edits also require their expected revision. Activation uses the server UTC date and its open accounting month, validates actual sources and an asset destination, reserves each candidate until explicit cancellation, and freezes terms and schedule. Cancellation and suspension append history. A Completed plan retains its source reservation because later reversal can undo its progress. Activation, candidate decisions, contribution acceptance, and candidate queries share this reservation rule. Cancellation releases it without deleting saving history. `replacePlan` cancels the original if needed and creates a linked editable Draft; activation validates it independently.

`recordContribution` accepts explicit allocations against an already Posted asset-to-asset transfer. It does not move money. Transfer capacity is shared across all plans in one mutation; unused capacity stays ordinary saving. Contributions preserve the transfer date and a separate server recording time. A failed recording leaves the Posted transfer unchanged. `reverseContribution` neutralizes the entire immutable contribution, restoring its capacity for new allocations; partial changes use reversal and replacements. Locked accounting periods do not block these planning corrections. Proposal creation carries a caller-supplied import reference, not proof of an import. Acceptance revalidates capacity, state, source reservation, activation date and destination; rejection creates no progress.

Progress rereads supporting transfers and current `by_reverses` facts. A transfer reversal voids progress while preserving its contribution history. A later independent withdrawal leaves progress intact. Declared opening progress is a separately labeled one-time assertion with provenance and unavailable-evidence attestation; it creates no transfer. Its through-date must precede the plan's frozen activation date, and declaration must precede the plan's first contribution. The endpoint refuses a declaration if an unreversed asset-to-asset transfer into that destination is already claimable on or after activation. Pre-activation imported movements cannot become contributions under ADR-0073, and their old declared attribution remains unverified. The initial endpoint records the declaration, not external import verification.

Schedule math takes principal, count, and chosen amount. It derives a nonnegative monthly rate by deterministic bounded present-value bisection, then rounds cumulative principal to whole minor units. Differencing cumulative principal fixes its total exactly. Each installment retains the chosen amount, and premium is its residual; no final amount adjustment is needed. Count is 1 through 600; total money must remain safe-integer minor units. The rate describes a behavioral commitment, not interest, investment yield, or a user-entered rate. This is the reversible engineering contract for the current Implied Self-Charge Rate language; the older ADR-0059 rate-entry alternative is not exposed.

A contribution fills outstanding frozen installments in order, including future installments as prepayment. Partial installments split principal and premium proportionally to their remaining frozen split. Principal then splits across unfinished sources proportionally. Both allocations use integer products and deterministic largest residual rounding, with ties resolved by frozen input order. Neither corrections nor prepayment recalculate the schedule.

`accounting.listPostedExpenses` reads the `by_workspace_policy_date` index for original `cash-expense@1` entries and returns original amount/date, expense lines, current eligible amount, linked source effects, and live reversal provenance. C02's agreed `journalSourceEffects` rows use `by_workspace_source`: Workspace, original source entry, producing entry, signed Expense delta, and safe positive `sourceSequence`. Posting assigns the sequence monotonically within each Workspace/source pair, starting at one, through the indexed mutation read. Retries add no sequence. The reader sums all effects exactly once; reversal of a correction adds its mirror rather than causing the original effect to be filtered. Original source reversal sets eligibility to zero. Corrections are never new selectable candidates. Linked Expense-to-Expense changes have delta zero; Expense-to-Income/Profile reductions have a negative delta. Any linked factual reduction lowers original eligibility. Recovery derives suspension on reads; `reconcilePlans` durably appends detected suspension. Activation freezes the latest source sequence for each source. The reader validates contiguous sequences and evaluates every subsequent eligibility prefix, even when producing timestamps are equal. A source reduction recorded during the active commitment keeps the plan suspended after a later restoration, derived from linked ledger history; the Owner cancels and replaces it. Finance and category operations write no Recovery rows.

The current base supports cash expense sources and source reversals. The original standalone C04 tests include synthetic reader fixtures. The reviewed combined `recoverySourceEffects.integration.test.ts` exercises the actual C02 correction/reversal writer and causal reader; it now runs with transaction limits enabled. The additional combined planning proof compares Budget actual Posted months with Recovery original-source eligibility without changing either context. Refund and Credit Note commands do not exist in this base; future writers must emit the same linked source facts through Posting.

`progress` separates verified and declared totals, displays current destination balances, and returns immutable history and void/correction flags. A historical `asKnownAt` filters recorded events, supporting reversals and source effects, and returns only commitments activated by that instant. It omits current destination balances in historical reads. It does not reconstruct edited historical Drafts or provider state.

`monthlyWaterfall` derives unpaid earlier installments as carried shortfalls without penalties, current installments and the Combined Recovery Payment. It allocates planning cash to oldest shortfalls, current installments, eligible unreserved candidates by source date, optional future installments, and ordinary saving. Shortfalls have no accounting effect. This read is a current planning projection, not a stored Month Close snapshot.

Computed cash reads selected Workspace asset profile balances and subtracts explicit essential spending, taxes, reserves and external obligations. Profile selection is an Owner assertion of liquidity, not an inferred product guarantee. Entered cash is an attested net amount, so protections are recorded without subtracting them twice. Both return protection provenance and `unmodeledObligationsProtected: false`. No endpoint claims that missing obligations were protected automatically.

Local convex-test proof exercises actual public handlers and real schema/store/Posting behavior. It proves no deployed OCC, provider authentication, native-device or physical-device behavior. Deployment and physical-device verification are outside C04.
